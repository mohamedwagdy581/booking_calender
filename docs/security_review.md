# Security and reliability review — 14 October 2026

This is a source and local-artifact review, not a live penetration test. No
database policies, server secrets, deployed functions, or client installations
were changed. Existing uncommitted changes were preserved.

## Critical: previously distributed SMTP credential

`pubspec.yaml` included `.env` as an asset. Inspection of the previously built
client APK confirmed a nonempty `GMAIL_APP_PASSWORD` in its bundled `.env`.
The Windows release used the same asset configuration. No credential values are
included in this report or tool output.

**Revoke/rotate that Gmail app password now.** Existing distributed binaries and
older local build artifacts still contain the old credential; source changes do
not remove it from them. Send replacement builds after rotation. This issue was
missed during the earlier packaging work.

Future builds now include only `assets/config/public.env`. Generate it with:

```powershell
python tools/generate_public_config.py
```

The generator allows only the Supabase URL and public anon/publishable key and
rejects service-role/secret keys. `.env` stays local and is no longer an asset.
The checked client key has the `anon` role; it is intentionally public, and access
must be protected by authentication and RLS. See [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys).
Generate this file in CI before Flutter commands; do not upload `.env` as an artifact.
Legacy `EmailService` uses client-side SMTP and has no current callers. Do not
re-enable it or put mail credentials back into a client asset; use a server sender.

## Server findings requiring separate work

| Priority | Evidence | Required change |
|---|---|---|
| High | `supabase/migrations/20260215_create_device_tokens.sql` grants public select/insert/update/delete with unrestricted policies. | Authenticate token registration and restrict ownership to the current user. Verify actual live policies before changing them. |
| High | `send-push` trusts caller-supplied messages and uses a service-role client to fetch all device tokens, without an explicit user/booking authorization check. | Verify the caller's user token, authorize the booking/action using RLS, derive the message on the server, and limit recipients to authorized users. |
| High | `send-email` accepts arbitrary recipient/message data and interpolates it into HTML, without explicit user authorization or payload validation. | Authenticate and authorize recipients, validate fields/lengths, escape HTML, and add rate limits. |
| High | Booking/profile RLS definitions are absent from this checkout. UI role visibility alone cannot protect data. | Verify live policies for reads, writes, reports, and role changes, using staff/admin/anonymous accounts. |
| Medium | Reference numbers are generated by reading records and adding one to the maximum. | Allocate numbers atomically on the server with a unique constraint; concurrent clients and API pagination can otherwise produce duplicates. |

Gateway JWT validation alone is not a substitute for authorizing a user's action.
The deployed gateway configuration was not inspected. See [Edge Function authentication](https://supabase.com/docs/guides/functions/auth).

## App fixes

- Authentication redirects and auth-change refresh now protect direct workspace
  and Search navigation. Backend policies are still required.
- The standalone mobile Search route now provides the BookingCubit needed by
  its details/edit actions; opening a result previously could fail with a
  missing-provider error.
- Search values are quoted and escaped as PostgREST values, preventing reserved
  punctuation from becoming filter syntax. See [PostgREST URL grammar](https://docs.postgrest.org/en/stable/references/api/url_grammar.html#reserved-characters).
- Search and booking reads ignore stale completions and safely handle a closed
  Cubit. Clearing Search invalidates its pending response.
- Calendar errors stop triggering automatic retry loops on every rebuild and
  offer an explicit Retry action.
- Add-booking success carries the saved database record into the print action;
  printing no longer uses the provisional reference number.
- Failed reference-number reads propagate an error instead of silently reusing
  `1000`. This does not solve cross-client allocation races.
- Editing preserves archive metadata. `copyWith` supports replacing or explicitly
  clearing the tax number; ordinary copies retain it.
- Nonfinite amount input (`NaN`, `Infinity`) is rejected, and reactive calculations
  no longer throw. Date selection clamps an expired initial date to its minimum.
- Password submission preserves significant whitespace. Auth completions no
  longer emit after disposal, and Splash handles already-resolved auth state.
- Legacy Dio refresh attempts are bounded, preventing recursive 401 retries.
- Android notification visibility is private rather than public on the lock screen.
- Performance PDFs use bundled fonts and paginate employee rows without requiring
  a font download. Quotation generation no longer mutates the app's global locale;
  quotation amounts retain cents rather than rounding them away.

## Other remaining limitations

- Profile edit/password-change buttons are placeholders. Password-reset completion
  and recovery deep links need a complete tested flow.
- Some service methods turn network errors into empty data; reporting should
  distinguish an empty result from a failed request.
- Push token ownership is not re-bound on every auth change, and sign-out does not
  unregister a token. Resolve this together with owner-restricted token policies.
- Legacy Dio targets a demo API and uses shared-preferences token storage; it has
  no active feature callers. Remove it or design production transport/storage
  before enabling it.
- Android release uses the debug signing configuration; establish protected release
  signing for production updates. Windows installers are not code-signed.
- Large text in fixed quotation sections may still exceed PDF page constraints;
  add length limits and representative document layout tests.

## Validation scope

Regression tests cover concurrency, route policy, numeric input, archive/tax
metadata, public-config allowlisting, and an 80-employee offline report, alongside
the existing suite. Live RLS, function authorization, recovery links, signing,
notification delivery, and real client devices require separate verification.
